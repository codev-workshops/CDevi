# Contract: Review Center — `/reviews` and `/reviews/{pullRequestId}`: regions, states, accessibility, and the Workflow Detail marker

Normative for `apps/web/app/(app)/reviews/` and the "Pull request" extension of `apps/web/app/(app)/workflows/[id]/WorkflowDetailScreen.tsx` (User Story 6). Every element is an `@cdevi/design-system` component (1.4.0; 1.5.0 only if Phase 13d confirms one of the two candidate gaps in plan.md Part F — the default resolutions below need no package change). Read model: `PullRequestReviewView` and `ReviewListPage` (data-model §40); pure helpers from `@cdevi/contracts/review-model` (`REVIEW_LANES`, `LANE_WORDS`, `SEVERITY_WORDS`, `BLOCKING_WORDS`, `blockingToDesignSystem`, `FINDING_STATE_WORDS`, `REVIEW_STATUS_WORDS`, `CYCLE_STATE_WORDS`, `readyForMerge`, `blockingOpenCount`, `blockingNoticeText`, `reviewHref`, `findingAnchor`) and `evidenceHref` from `/agent-run-model`. Decisions Q1–Q6 (plan Part F) are binding: **no saffron on either screen**; Create Issue records intent only; FR-035 header counts untouched; the FR-022 marker appears here and on Workflow Detail only.

## 1. Routes and composition

- `reviews/page.tsx` (server): `getReviewList(query)` (`lib/session.ts`) → `apiFetch<ReviewListPage>('/api/reviews?project=&status=&cursor=', { cookie })`; the `project` search param scopes like `/requirements`; any error renders §5.11 *not available*. → `<ReviewsScreen initial me />`.
- `ReviewsScreen.tsx` (client): renders §2 from `ReviewListPage`; "Load more" appends the next page by `nextCursor`; subscribes with `subscribeInboxStream({ onChange })` (org-wide, debounced 300 ms) → refetch the **first** page and replace the loaded pages (FR-034); no scroll reset.
- `reviews/[id]/page.tsx` (server): `getReviewCenter(id)` → `apiFetch<PullRequestReviewView>('/api/reviews/{id}', { cookie })`; 400/401/403/404/5xx all render §5.9 *not available* (no existence leak). → `<ReviewCenterScreen initial me />`.
- `ReviewCenterScreen.tsx` (client): renders §3 from the read model only; subscribes with `subscribeInboxStream({ onChange, workflowId: pullRequest.workflow.id })` (debounced 300 ms) → refetch `GET /api/reviews/{id}` and replace the whole model; keeps the selected tab, filters, an open Dismiss form and scroll position. Actions call `POST /api/reviews/{id}/findings/{findingId}/{dismiss,fix,issue}` with the CSRF header the Approval Center uses, then apply the returned `FindingActionResult` immediately (finding, cycle, `readyForMerge`, `blockingOpenCount`) — the SSE refetch that follows confirms it.
- Shell (`AppShell`, `Side`, `Main`, `Panel`) from `(app)/layout.tsx`; `/reviews` becomes a **built** section (`BUILT_SECTIONS`), so the `Side` nav highlights "Reviews" on both routes. Header `NavItem` counts (FR-035) are **unchanged** (Q5).
- Workflow Detail marker (§4): `WorkflowDetailScreen.tsx` renders a "Pull request" row when `detail.pullRequest !== null`, linking to `reviewHref(pullRequest.id)` and carrying the FR-022 marker (Q6). The Approval Center is **not** changed.

## 6. Keyboard and focus

- Tab order (Review Center): crumbs ("Reviews" → "PR #n") → header links (pull request (new tab) → requirement → workflow) → 3.4 notice (not focusable; announced by `role="alert"` on load) → `GateList` rows (static, not focusable) → `Tabs` tablist (one tab stop; `ArrowLeft`/`ArrowRight` between "Findings" and "Review cycles", `Home`/`End`) → active panel: filters (`Segmented` roving, `Chips` as buttons) → each finding's evidence links → "Apply Fix" → "Dismiss" → "Create Issue" (or the open form: `TextArea` → "Confirm dismiss" → "Cancel") → next finding; Cycles panel: "Inspect run" links only.
- `#finding-{n}` in the URL (from Workflow Detail, the Inbox, or a shared link): selects the Findings tab, clears filters that would hide it, scrolls the row into view and moves focus to its `<li tabIndex={-1}>` so `FindingRow`'s heading is announced.
- "Dismiss" opens 3.10 and moves focus to the `TextArea`; `Escape` or "Cancel" closes the form and returns focus to "Dismiss"; after a successful dismiss, focus moves to the finding's state pill container (`<li>`) and the live region announces "Finding {n} dismissed".
- After "Apply Fix": focus stays on the row (`<li>`); the live region announces "Fix requested — Review Cycle #{n}"; the Cycles tab label count updates; the tab does **not** switch automatically.
- After "Create Issue": focus stays on the row; the live region announces "Issue requested for finding {n}".
- Every link, tab, chip and button is a native `a`/`button` with the design-system focus ring (no `outline: none`); external links state "(opens in a new tab)" in their accessible name.
- `/reviews`: crumbs → filters → rows (title link) → "Load more".

## 7. Saffron decisions (DR-02 — justified per screen)

| Screen | Saffron control | Justification |
|--------|-----------------|---------------|
| `/reviews` — every state | **none** | A list; nothing waits on a person here |
| Review Center — every state | **none** (Q4) | The person-needed action on a pull request is the **merge approval**, which the Approval Center owns with the one saffron action. Apply Fix, Dismiss and Create Issue are engineering actions on individual findings, none of which is "the one thing a person must do"; three saffron buttons per row would erase the meaning of saffron. The word "blocking" renders through the design system's normative `Pill variant="needs-you"` mapping — a classification word, not a call to action. If gap (b) lands (`Notice tone="needs-you"`), this row records that the notice border is the screen's second saffron surface and that it is still not a control |
| Workflow Detail — "Pull request" row | none | A link and a pill; the workflow's existing saffron decision is unchanged |

Tests assert `.cd-saffron` **button** count **0** in every §5 state of both screens, and that the Workflow Detail saffron count is unchanged by 4.1.

## 9. Accessibility acceptance

- axe (WCAG 2.2 AA rules) passes in every §5 state in component tests and on the not-ready, ready, viewer, dismiss-form and running-cycle screens in Playwright (SC-010).
- No information is conveyed by colour alone: review status, lane result, severity, blocking class, finding state, cycle state, merge readiness and evidence accessibility are all words.
- The FR-022 notice is a `role="alert"` (or `status` if gap (b) lands) region rendered on first paint so it is announced on load; it is never inside a collapsed, filtered or tabbed container.
- No raw model reasoning is present in the DOM in any state (SC-009): the component test renders every fixture and asserts the absence of any `reasoning`/`chainOfThought` text; a fixture typed with such a field fails `tsc` (the contract has no such key).
- Every action is reachable and completable by keyboard; the Dismiss form traps nothing (no modal) and restores focus on close; disabled buttons keep their `Help` text associated via `aria-describedby`.
- `<time dateTime>` on every timestamp; counts are plain integers with their term; the `Meter` has a text equivalent.

## 10. Performance (plan Part F budgets)

- Initial content (header + lanes + first finding) ≤ 2 s p95 (SC-007); the whole model is in the server render; lists bounded (findings 50, evidence 20 per finding, cycles 20, list page 50, lanes 7).
- `inbox.changed` → updated finding state / cycle counts ≤ 5 s p95, ≤ 1 s median (SC-003, FR-034); debounce 300 ms; one refetch per burst; the action response is applied immediately so the user never waits for the SSE round trip.
- Route JS ≤ 200 KB gzip for `/reviews` and `/reviews/[id]`; browser imports only `@cdevi/contracts/review-model`, `/agent-run-model` (for `evidenceHref`/`agentRunHref`), `/vocabulary`, `/read-model` (no zod in the client bundle).
- Filtering is client-side over ≤ 50 rows; no request per filter change.
- Workflow Detail: the "Pull request" row adds no extra request (the field rides `GET /api/workflows/{id}`).
